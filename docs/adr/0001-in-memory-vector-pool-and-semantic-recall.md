# ADR-0001: 采用进程内向量缓存池与两级召回替代外部向量库及 MySQL 读 BLOB

## 状态
Accepted

## 背景与问题 (Context)
在原有的 P2 语义召回读路径中，每次 Feed 请求都会执行 `LoadVectors`，从 MySQL 批量读取 500 条视频的 1536 维 float32 向量（单次传输约 3.07MB BLOB），高并发下造成极大的数据库网络与磁盘 IO 压力；且候选池硬编码截断在最新 500 条，长尾历史视频完全失召；此外，读路径上不感知翻页时间游标，导致连续翻页时反复推荐同一批高分视频；甚至在读链路上尝试引入外部 LLM 进行 RPC 精排，严重违反了推荐系统读路径必须高可用、低延迟（P99 < 50ms）的铁律。

## 架构决策 (Decision)
1. **进程内向量缓存池 (In-Memory Vector Cache Pool)**：
   在 Go 进程堆内存中维护并发安全的向量缓存结构，常驻缓存最近发布的 2,000 条活跃视频向量（1536 维 float32 向量在 2,000 条规模下仅占约 12MB 内存）。在线读请求直接在本地内存进行余弦点积运算（2,000 次计算耗时 <2ms），完全消除向 MySQL 读取大 BLOB 的 IO 与网络瓶颈。
2. **两级候选召回机制**：
   主路直接使用内存池中的 2,000 条活跃视频；长尾旁路基于用户近期高频点赞的 Top 标签倒排索引，定向提取 50~100 条历史视频 ID，按需查询向量合并参与打分，兼顾时效热度与长尾覆盖。
3. **滑动曝光去重 (Exposed Filter)**：
   服务端基于 Redis Set 维护用户近期已看视频集合（Key: `feed:exposed:{uid}`, TTL: 15~30分钟），每次下发后异步追加，召回阶段前置过滤，确保跨页翻页时自然推荐次高分内容，杜绝相邻页重复曝光。
4. **双轨向量生产与游标巡检**：
   视频发布后通过异步事件秒级触发向量化；后台补偿 Worker 改造为基于主键游标（`WHERE v.id > ? ORDER BY v.id ASC LIMIT ?`）的平滑推进巡检，彻底修复无游标导致的 500 条外新增视频漏算 Bug。
5. **读链路完全剥离 LLM RPC**：
   明确语义召回依赖 Embedding 模型，精排阶段采用本地轻量多特征加权打分（语义分+时间衰减+热度加权，耗时 <0.1ms）。外部 Node Sidecar / 大模型严格限制在离线/近线内容理解与 Agent 场景，绝不进入在线读链路。

## 权衡与影响 (Consequences)
- **优势**：
  - 接口延迟显著降低，语义召回 P99 降至 8ms 以内，Feed 吞吐上限从数十 QPS 跃升至 1000+ QPS。
  - 零外部向量中间件依赖，单机架构轻量、高内聚，完全可自愈、易维护。
  - 面试叙事逻辑极其扎实，对性能数字、内存开销与架构权衡有据可依。
- **代价与边界**：
  - 单机内存池容量建议控制在 5,000 条以内（约 30MB 内存），当全库视频量增长至百万级以上且长尾召回要求极高时，需平滑演进为专用分布式 ANN 向量检索集群（如 Milvus 或 HNSW 索引）。
